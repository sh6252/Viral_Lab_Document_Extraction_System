## 5. מוכנות ל־commit ולהגשה

**קובצי המקור מוכנים לסקירת commit אטומי בענף השחרור**, עבור גבולות הדמו
המקומי המתוארים. הבדיקות הנדרשות הזמינות עברו וה־diff נבדק. אין staged
files ואין commit חדש, בהתאם לאיסור המפורש במשימה. אישור commit אינו
אישור push או deploy. קובצי מקור חדשים כלולים במפורש בארכיון גם ללא staging.

ה־manifest מתעד hash של overlays המקוריים וגם hashes של התאמות השחרור.
`source-files.json` מקפיא את כל התכולה להגשה. אימות/אריזה חוזרת:

```powershell
python scripts/release_snapshot.py
python scripts/release_snapshot.py --zip C:\path\to\new-submission.zip
```

הפקודה השנייה מחייבת נתיב פלט חדש. אין להריץ `git add .` מתוך העץ המקורי
כדרך להכנת השחרור; הסקירה וה־commit העתידי שייכים לעץ השחרור בלבד.

## 6. פריסה: חסמים לפי חומרה

**קריטי לציבור:** authentication/authorization יישומיים אינם מחוברים ל־demo,
ואף endpoint החילוץ הכללי פתוח ברמת היישום. גבול loopback אינו מתאים
להמרה לשירות ציבורי על ידי bind/proxy בלבד. דרושים TLS וגבול גישה מאומת.

**קריטי להדגמה מלאה סינתטית בענן:** אין מסלול durable עם provenance סינתטי
אמין; seeder חסום בכוונה ו־local OCR אינו ממומש. אין לשתול mock כ־LIVE
או להפעיל Gemini כתחליף ללא אישור. נדרשת החלטה על demo מקומי מוגבל או
משימת המשך נפרדת וממוקדת. לא פותחה יכולת זו במסגרת הכנת השחרור.

**קריטי לפני כתיבה בענן:** מסד סינתטי חדש, secrets חדשים, migrations
0001–0003 ואימות CHECK/readiness. אין הרשאה לשנות את `viral_lab` המקומי.

**לא קריטי להגשת קוד/דמו פרטי:** חסרים קובצי deployment/CI, lock Python
נייד מלא, בדיקת Linux, worker והתאוששות עיבוד, readiness למסד, מדיניות
retention, ניטור, בדיקת עומס וגיבוי/שחזור ענן. אלה מהותיים לשירות production.

## 7. המלצת hosting והצעדים הבאים

VM Linux יחיד עם PostgreSQL בדיסק מתמשך, Uvicorn יחיד ו־nginx עבור build
ה־React. HTTP והמסד ב־loopback בלבד; גישה פרטית דרך SSH עם מפתח והרשאת
IP. אין לפתוח localhost-demo לציבור. זו התצורה הפשוטה ששומרת על גבולות
המערכת בזמן שנותר; אין תוספת של Redis/Celery/מיקרו־שירותים.

הצעדים המדויקים, כולל entry point, DSN ומיגרציות, frontend proxy/Origin,
secrets, health ו־SSH tunnel, נמצאים ב־[נוהל הפריסה](DEPLOYMENT_HE.md).
המלצת השימוש בשרת סטטי ל־build תואמת את
[הנחיות Vite](https://vite.dev/guide/static-deploy.html), והגישה הפרטית מבוססת
על [OpenSSH local forwarding](https://man.openbsd.org/ssh).

המשימה הבאה המומלצת: **סקירה ואישור commit של מועמד השחרור**, ואז בחירה
בין הגשה עם הדגמה פרטית מוגבלת לבין אישור משימת provenance סינתטי מצומצמת.
רק לאחריה ואחרי אימות Linux יש לאשר פריסה פרטית. לפריסה ציבורית נדרש auth
נוסף; אין כאן הבטחה שאפשר להשלים אותו ואת כל הבדיקות עד הדדליין.

## 8. פרטיות והערכה

לא שונו מודל, prompt, normalization או review policy מעבר להעתקה המדויקת
של העבודה שכבר הייתה במקור. נכלל ה־prompt הקיים
`he-commitment-v3-lab-commitments`, השונה מה־base ההיסטורי. לא הורץ ניסוי
AI, לא שונתה ground truth ולא בוצעה השוואת איכות live לבסיס הקודם;
זהו חוסר אימות ידוע של השינויים שקדמו למשימת השחרור, לא מדד שיפור.
נתוני dev ו־holdout לא אוחדו; מסמכי holdout לא נכללו בהגשה. אין טענה
לדיוק production מהדאטה הקטן או מבדיקות software.

המסד העסקי וקובצי ההגדרות נשארו ללא שינוי. אין מסמכים רפואיים או סודות
בארכיון, וההגנה מ־Excel formula injection נבדקה בבדיקות הקיימות.
הגדרת גבול SSH אינה תחליף להרשאות יישומיות לעבודה אמיתית במידע רפואי.
